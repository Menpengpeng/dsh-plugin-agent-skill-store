# 翻译规范（Agent Skill 中文描述）

你要把一个批次里的英文 skill 描述翻译成中文，供「Agent Skill 商店」插件展示。

## 输入 / 输出

- 输入：`agent-skill-store/data/zh-batches/in-XX.json`，数组，每项 `{ id, name, desc }`。
- 输出：`agent-skill-store/data/zh-batches/out-XX.json`，**同样长度、同样顺序**的数组，每项 `{ id, zh }`。
- `id` 必须原样照抄，**一个都不能少、不能多、不能重排**。输出用 UTF-8（可带 BOM）保存。

## 翻译要求

1. **中文意译**，不要逐词直译。目标是一眼能看懂「这个 skill 是干什么的」。
2. 长度 **20–70 个汉字**，一个句子说完；原文很长时只保留主干用途，不要罗列所有细节。
3. **产品名、框架名、CLI 命令、文件名、API/SDK 名、模型名、格式名保持英文原样**，例如
   Playwright、Figma、MCP、SKILL.md、npx、Claude Code、Cursor、pandas、OpenAPI、Notion、Stripe。
   不要在英文名后面加中文括号注释。
4. 不要出现「该 skill」「这个技能」「本文档」这类主语套话，直接写用途，
   例如「把设计稿转成可用的 React 组件」而不是「该 skill 用于把设计稿转成…」。
5. 不要结尾加句号，不要加引号，不要加「适用于」这类空话开头。
6. 原文是「When to use: …」这类条件句时，翻译成用途陈述，不要保留「何时使用」的字面结构。
7. `desc` 为空或明显是噪声（只有徽章文字、只有 `deprecated` 之类）时，根据 `name` 写一句合理的
   用途描述；`name` 也看不懂就写「名称含义不明，建议打开原始链接确认」。
8. 原文提到的数量、版本号（如 22 playbooks、v1.1）保留数字，单位译成中文。
9. 专有英文术语首次出现可保留英文，不要造生硬的中文译名；例如 agent 不要译成「代理」，
   直接写 agent 或「智能体」都可以，但同一批次内保持统一。

## 质量自检

产出后自己检查：

- 条目数与输入一致；
- 没有残留整段英文；
- 没有乱码（因为文件是 UTF-8，若看到 `?` 或方块说明写错了编码）；
- 每句都是完整可读的中文。
